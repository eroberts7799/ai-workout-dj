## Problem Statement

Runners and cyclists who want music matched to their workout have two bad options: static playlists that ignore what's happening, or hand-timed DJ mixes that take real effort to build and drift out of sync the moment pace varies. Ethan wants an AI DJ that ingests real-time workout data (live heart rate from his Garmin, position in a structured Runna workout, route elevation from Strava) and controls Spotify so that the right *part* of the right song lands on the right *moment* of the workout — the drop hits as you crest the hill, the buildup starts as the hard interval approaches.

This is a learning project: the explicit goal is leveling up on real-time data, music APIs, and AI, dogfooded on Ethan's own training.

## What Makes This Cool

Every existing product — RockMyRun, FitBeat, Beat Mix, and Spotify's own preset-based Running Mode (relaunched July 2026) — does **reactive tempo matching**: read current effort, pick a song with matching BPM. A thermostat.

This project does **anticipatory choreography**: because the training plan (Runna intervals, known to the second) and route (Strava elevation profile) are known *before the workout starts*, the DJ can build toward moments the way a human DJ builds toward a drop. The framing that unlocks it (from the cross-model second opinion): this is **video-game adaptive audio middleware for your body** — Wwise/FMOD-style horizontal re-sequencing where the hill is the boss fight.

Two mechanics fall out:

1. **Loopable buffer sections absorb timing uncertainty.** "Hill in 90s" becomes 70s or 130s as pace drifts. The DJ loops a 16-bar groove on its tagged loop boundaries and exits into the buildup at the **last loop boundary where ETA_remaining ≥ buildup_length** (re-evaluated at every loop boundary, not on a wall-clock cadence). Crucially, only the **exit point** in current playback is boundary-quantized; the **landing offset** in the destination track is continuous — the executor seeks to whatever position makes the drop land on the target moment (e.g., "seek to 1:02 so the drop hits t=4:00"). That's what makes ±1s drop timing achievable despite ~30s loop granularity. If ETA collapses faster than a loop iteration, or no tagged section fits the remaining time, the default is: cut early at the next section boundary, and if nothing fits at all, do nothing — let the current song play (silence of the mechanic, never silence of the music). This turns Spotify's no-crossfade jump-cut limitation into the core mechanic.
2. **The music becomes the interface.** No voice prompts, no glancing at the watch. Buildup starting = hill in 60 seconds. The drop is the reward for cresting. The athlete is being *conducted*.

Bonus artifact: the app logs every command against GPS/HR — rendered post-run as "your run as a DJ set" synced to the elevation profile. Shareable, and doubles as debugging telemetry.

## Constraints

- **Music platform: Spotify Premium** (what Ethan uses). Web API playback control (play/pause/skip/queue/seek-to-position) fully works for new apps. **Deprecated and unavailable**: audio features, audio analysis (song sections), recommendations, 30-second previews. Development mode caps the app at ~25 users; extended access requires 250K MAU. Acceptable per Premise 1.
- **No crossfading.** Spotify exposes one playback stream. All transitions are jump-cuts via seek/skip; the craft is cutting on musical boundaries.
- **Song-structure data must come from outside Spotify.** Weekend path: hand-tagging UI — mark **section boundaries only** (buildup start, drop, loop bounds); v1 cuts happen exclusively at section boundaries, not arbitrary downbeats. A tap-BPM + grid-snap tool can refine boundaries to the beat grid; per-downbeat hand-marking is explicitly out of scope. Growth path: `allin1` (github.com/mir-aidj/all-in-one) audio structure analyzer over legally purchased audio files (~$1/track for the training library), with `madmom`/`librosa` as backstops; results stored as JSON keyed by Spotify track ID, always human-correctable ("drop" is a vibe, not a label). **Known task for the allin1 phase:** timestamps from a purchased file can differ from Spotify's stream master (different leading silence/master) by hundreds of ms — each track needs a one-time offset calibration against Spotify playback (hand-tagging avoids this entirely by tagging against Spotify's own playback position).
- **Devices: Garmin watch + iPhone.** Garmin broadcasts heart rate over standard BLE (Heart Rate profile, 0x180D). Web Bluetooth works in desktop Chrome and Android Chrome, **not iPhone Safari** — so live in-browser HR is desktop/indoor only until a native app exists.
- **Where the conductor runs (v1 topology):** the conductor executes in **desktop Chrome**, full stop. Indoor/treadmill sessions are the v1 arena: desktop conducts, audio plays via the Web Playback SDK on the desktop or via Web API commands to the phone's Spotify app. Outdoor sessions are **not v1**: iOS Safari suspends a tab the moment the screen locks, so a phone-browser conductor dies mid-run, and desktop-at-home conducting an outdoor phone over LTE adds a network dependency we don't want to debug first. Outdoor is Phase 2+ (see Open Questions).
- **Spotify Connect device activation:** a backgrounded/idle Spotify app drops off the Connect device list and commands 404 until playback is transferred to it. The executor must transfer playback to the target device at session start and treat "device not found" as a re-activation, not an error.
- **Mid-run failure policy: degrade to normal playback, never interrupt the run.** Any command failure, network hiccup, or device dropout means the current song simply keeps playing; the conductor retries quietly and re-enters choreography at the next safe boundary. No error states that demand mid-workout attention.
- **User pause/stop:** a pause key freezes the workout clock (music keeps playing, choreography suspended; resume re-syncs via the resync keypress), and a stop key ends choreography entirely while leaving the current song playing. Distinct from failure degradation and from watch auto-pause (which stays off).
- **Auth:** access tokens expire (~60 min) — shorter than a long run. The app uses Authorization Code + PKCE with silent refresh from the conducting browser (no backend required; refresh must never require user interaction mid-session).
- **Training data: Runna plans synced to Garmin.** Only **time-based** interval sessions are deterministic; Runna plans also contain distance-based reps and open-ended warmups, which are not (they become ETA-predicted cases in the route phase). The weekend build targets one explicitly time-based session, hand-transcribed; API integrations come later.
- **Workout-clock sync:** the ±1s success criterion dies if the conductor's t=0 and the watch's t=0 drift. V1 uses a simultaneous-start ritual (start watch and conductor on the same "3-2-1-go") plus a single-keypress mid-run resync ("I am at the start of rep N — now"). Watch auto-pause is **unsupported in v1** — turn it off for conducted sessions.
- **Seek latency and position staleness are the existential unknowns.** If seek lands within ~±300ms, boundary-aligned cuts feel intentional; ±2s means buffer strategies before anything else. Equally: cutting on a boundary requires knowing the current position, and Web API position reports are stale by round-trip time. Hour one measures **both** — seek landed-position delta and position-read staleness — on both playback paths (SDK and Web API→phone). Compensation model: the executor issues each seek at `t_target − median_latency`, verifies landed position, and if measured jitter exceeds half a beat at the track's tagged BPM (default 250ms when a track has no BPM tag), absorbs the error via the loop-buffer mechanic instead of chasing precision.
- **Rate limits:** the loop mechanic implies a seek every ~15-30s plus position polling — plausibly enough to hit Spotify's dev-mode rolling-window rate limit. Measured alongside the hour-one spike; polling frequency is a tunable.

## Approaches Considered

### Approach A: The Weekend Conductor (minimal viable)
Browser app (Vite + React + TS, no backend, localStorage). Hand-tagged song structure (10 songs), hand-transcribed Runna intervals, Spotify Web Playback SDK on desktop / Web API to the phone's Spotify app when phone audio is wanted (still desktop-conducted). HR display-only via Web Bluetooth (desktop). Effort S, risk Low. Proves the magic moment in days; manual tagging won't scale past ~20 songs; no route awareness; indoor-only.

### Approach B: The Full Pipeline (ideal architecture)
Native iOS app (SwiftUI): CoreBluetooth for Garmin HR, GPS + Strava route elevation, Garmin/Runna workout import, `allin1` analysis service auto-building the song-structure database, background-safe outdoor operation, post-run DJ-set replay. Effort XL, risk Med-High. The real product, but weeks before the first magic moment with several integration risks stacked.

### Approach C: Engine + Flight Simulator (creative/lateral)
The conductor as a platform-agnostic TypeScript library: inputs are abstract event streams (time, HR, position), outputs are playback commands. Ships with a replay simulator feeding past Strava/Garmin activities at 10× speed against a mock player — tune DJ taste on a timeline UI without going for a run. Live sensors and real Spotify are just adapters. Effort M, risk Low-Med.

## Recommended Approach

**A grown into C.** Prove drop-lands-on-the-rep this weekend at A's scope, but write the scheduler/conductor as a pure library from day one (C's discipline, no extra cost) so the simulator, route support, and eventual native app are extensions, not rewrites.

Architecture sketch:

```
[Workout Plan]──┐
[Song Structure DB]──► CONDUCTOR (pure TS lib) ──► Cue list ──► EXECUTOR ──► Spotify
[Clock / HR / GPS]──┘   (re-solves every few s)      (latency-compensated seeks on section boundaries)
```

- **Conductor** (pure, testable, no I/O): given a workout timeline, tagged songs, and current state, emit the next cues. This is where the learning is.
- **Adapters**: clock (weekend), BLE HR (desktop weekend, native later), GPS+route ETA (phase 2), replay-from-Strava (simulator).
- **Executors**: Web Playback SDK (desktop), Web API→phone Spotify (phone speakers/headphones, desktop-conducted), mock player (simulator/tests). **Executor contract includes structured logging**: every issued command, its measured latency, and current sensor/plan state, timestamped — this is both the debugging telemetry and the data source for the post-run "your run as a DJ set" replay artifact (built in the simulator phase).

## Success Criteria

- **Weekend:** on one real **time-based** interval session (treadmill/indoor, watch auto-pause off, simultaneous-start ritual), the drop lands within 1 second of a hard-interval start, three intervals in a row, with transitions cut on section boundaries.
- **Phase 2 (simulator):** replay a past Strava activity and watch a coherent DJ set assemble on the timeline; tweak a rule and see the set re-choreograph.
- **Phase 3 (routes):** on a pre-planned outdoor route, the buildup begins within ±15s of the ETA-predicted hill approach and the drop lands within ±5s of the crest.
- **Throughout:** Ethan chooses this over his regular playlist for real training sessions — the only retention metric that matters for a personal tool.
